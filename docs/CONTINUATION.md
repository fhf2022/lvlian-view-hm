# 跨设备接续 · 第一版

状态：随 1.0.11 正式发布，已完成手机→平板图片、音频、视频的正常接续与返回检查；异常组合、反向及其他设备仍待验证。建议两端均安装 1.0.11；1.0.9 HAP 不包含此功能。

## 使用范围

使用系统的应用接续入口，从一台设备转到另一台设备继续浏览。系统要求两端登录相同华为账号、开启接续，设备联网且打开 WLAN、蓝牙，并安装同一个应用。具体入口和设备支持范围以系统为准，应用没有增加独立的发送按钮。

| 当前页面 | 第一版行为 |
| --- | --- |
| 个人或共享目录 | 恢复目录、排序、视图和首个可见条目 |
| 大图片文件夹 | 使用当前已经完整加载的目录索引，保持图片顺序和时间轴数据 |
| 从普通目录打开图片 | 打开当前图片，可继续左右浏览；返回到所在目录 |
| 普通音乐 | 恢复曲目、进度与播放/暂停状态，播放列表由同目录音频重建；返回定位到该文件 |
| 普通视频 | 恢复视频位置及播放/暂停状态；返回所在目录 |
| 搜索、多选、投屏、画中画、传输页、设置 | 源端暂不开放发起接续 |
| 系统选择器、上传确认、文件操作弹窗、切换动画 | 源端暂不开放发起接续 |

目录索引不完整、正在操作文件或目录超过 50,000 条目时不开放接续；快照还有 16 MiB 上限，超限会拒绝准备。源端的图片缩放、临时旋转、音量、画中画及投屏会话不迁移。

已完整挂载的目录可以在后台校验新鲜度时接续；完整性以当前目录的 key、索引完成标记、分页状态判断，不等待后台校验请求结束。正在切图、媒体打开／关闭、播放控制、进度跳转和弹层操作时仍暂停接续，稳定后恢复。

## 账号与现有任务

- 华为同账号由系统判断；应用另外校验相同 NAS 云盘 ID 和真实 NAS 用户 UID，不以显示名称或相同用户名替代 UID。
- 目标设备使用自己的登录会话。不会传密码、访问令牌、下载链接或登录状态，也不会自动退出目标设备已有账号。
- 目标账号不匹配时通过底部通知提示登录相同 NAS 和账号；用户自行完成登录后继续，系统返回可取消，整个接收过程最多等待 90 秒。
- 原设备保留应用，上传下载任务留在原设备。目标设备已有队列也不重建、不清空，不迁移后台任务或未提交的文件操作。
- 音频和视频在准备时暂停原设备播放，准备失败或取消则恢复原播放状态。系统接受导出以后若后续跨设备恢复失败，当前没有业务确认回执；此时原设备媒体保持暂停，可手动继续。

接收资格与源端发起资格分开判断。已完成开屏授权、账号匹配的接收端不再因为当前打开图片、音频、视频、搜索、多选、设置或目标选择器而拒绝接续；恢复前撤下旧页面的弹层，按下文策略处理已有播放，取消旧导航及未提交的界面操作，并拒绝晚到的旧弹窗结果。后台传输和登录会话保留。首次授权、账号不匹配及同时向外发送仍遵守原有边界。

## 数据与返回路径

小型 Want 参数只携带协议版本、请求 ID 和系统分布式会话 ID。目录路径、账号匹配标识、排序、媒体位置和精简的当前目录条目写入 JSONL 文件，再通过分布式数据对象的 `Asset` 传输。不传递递归文件树、原图、缩略图、原设备的私有 URL 或缓存路径作为远程文件标识。

源端按 200 条一批写入并让出事件循环；接收端分块读取和解析，校验大小、有效期、重复路径、条目数量、当前文件及目录边界。传输临时文件在接收完成或取消时清理；源端保存最多 10 分钟，进程重启后的首次接续也会清理过期文件。

接收端先用自己的会话向 NAS 请求根目录和当前目录第一页，核对访问权限，再同步提交完整目录、顶栏和导航历史。冷启动和热接收均使用应用图标开屏占位，恢复成功后撤下；账号不匹配时撤下占位并提示登录，允许用户操作登录页。传入索引是发起时的快照，不代表 NAS 在接收时仍完全相同；文件后续变化依靠刷新及实际读取结果处理。

返回历史重新构建为“目标账号可见的根 → 祖先目录 → 当前目录”。媒体场景都以当前媒体路径作为文件列表锚点，先渲染并定位文件列表，再打开图片、音频或视频。关闭媒体回到该文件位置，继续返回逐层定位到刚退出的子文件夹。父目录只在返回到它时加载完整索引；不把目标设备原有历史拼接进来。图片打开采用普通淡入，音频直接挂载播放页，不伪造另一台设备上的共享元素坐标；正常的本机打开／返回动画保持原实现。

音频和视频位置使用现有播放器准备与 seek 链路。音频在 prepare 后等待本次 seek 完成，再按源端的播放／暂停状态继续；达到或超过总时长时从零开始。恢复准备期间可以取消；准备完成后的播放回调沿用媒体会话 token，不继续依赖已经结束的传输 token。

## 维护入口

- `ContinuationModel.ets`：协议、精简条目、数据校验、账号校验与祖先路径。
- `ContinuationSnapshotStore.ets`：有界异步文件读写、过期清理。
- `ContinuationManager.ets`：系统可接续状态、分布式对象、取消/超时和页面注册。
- `EntryAbility.ets`：`onContinue`、冷/热接收与窗口恢复。热恢复复用已加载页面，不重复初始化队列。
- `Index.ets`：页面资格判断、捕获和恢复，复用现有媒体、目录和滚动逻辑。

系统版本协商要求目标至少为 1.0.10（`versionCode=1000010`），低于此版本提示更新并拒绝接续。目录、图片和视频保留协议 1；新增音频使用协议 2，修复版接收端同时支持协议 1／2。早期 1.0.10 调试包未实现音频，会拒绝协议 2，两端应安装本次修复包。API 26 本次没有增加 `DISTRIBUTED_DATASYNC` 或其他用户授权权限。

## 媒体入口补修

- 图片资格判断曾误用 `viewerInteractionUnlocked`；该字段表示看图结束后释放底层文件列表的交互，稳定看图时刻意为 false，不能拿来判断图片是否就绪。改用已有转场／关闭／模态拦截和已提交图片身份。
- 旧版明确排除了音频，且协议和恢复分支均缺少音频。现在接入同一快照、账号校验、当前目录和祖先路径链路，不另建音频导航树或传输通道。
- 真机复现完整目录的后台新鲜度校验使 `timelineIndexing=true`，即使已挂载索引完整也一直禁用媒体接续。取消该冗余限制，仍保留实际不完整目录、分页和账号边界校验。
- 媒体瞬时控制和转场结束后重新更新系统任务状态；音频 seek 完成／取消由播放器现有 seek 生命周期通知，避免使用定时轮询或逐帧网络／目录操作。任务状态日志只包含 active／inactive，不记录路径、账号或快照内容。

## 当前验证与待验证

### 2026-10-25 反馈界面调整

- 最初打开文件的源设备保留当前目录／图片／音频／视频画面，不切到首页或开屏；底部玻璃条提示“正在流转到另一设备”，2000ms 后消失。导出准备期间保留透明输入保护，系统返回仍可取消；不卸载原页面或媒体组件。
- 接收设备在冷启动和热接收时都使用应用图标开屏占位，直到内容恢复完成，不额外显示加载转圈或文字；系统启动窗也使用真实应用图标，避免 ArkUI 首帧之前没有品牌反馈。隐私授权流程保留。
- 源端流转提示、账号提醒及普通错误共用页面 UIContext 的原生 Toast，复用已有沉浸光感材质，显示 2000ms；相同提示在两秒内合并。源端导出阶段只提示一次，不随页面状态刷新反复弹出。提示代表正在交接，不声称目标已恢复成功。
- 原生 Toast 的底距从导航安全区顶部起算，因此以“共享底栏内容避让（额外 12vp）减去导航安全区”定位，避免重复计算导航栏高度。没有导航栏的上分屏／小窗仍保留最小窗口边距。
- 不增加通知定时器、自绘悬浮层或模态错误对话框；普通失败保留一次触觉反馈，删除确认和系统权限申请仍按原交互处理。后台接续错误保留到应用回到前台后再提示。
- 源端不退出原本就是既有策略，本轮没有改变该策略。原实现仍等待远端 `save()` 完成才返回 AGREE；现改为写完快照、激活会话并发起保存后先放行目标启动。原对象和文件仍按既有期限保留，接收端继续等待 `restored` 后读取校验数据。依据官方数据迁移说明：源端退出时必须等待持久化；本项目保留源端，因而将该等待移出启动路径。
- AGREE 前的准备失败仍恢复原播放；AGREE 后异步保存失败只提示并记录阶段，不擅自恢复源端播放或撤销正在恢复的目标。旧对象或旧代次的迟到失败不能覆盖新接续。仍没有业务完成回执，不能把保存完成当作接收成功。
- `tests/notice-feedback-regression.cjs` 覆盖时长、底距、重复错误、源端通知／接收占位、账号、启动／后台延迟和窗口销毁。既有接续回归已转入正式 `tests/continuation-regression.cjs`，新增远端保存未完成时放行、异步保存失败、迟到失败隔离和准备期间取消等检查，均通过。
- 最终包手机→平板的图片热接收、强停目标应用后的冷接收均通过，双方关闭图片返回正常。截图确认源端仍显示原图及底部玻璃通知，接收端冷热两次均为应用图标占位，随后正常恢复图片。此小目录的源端 `Export requested` 到 `Export prepared` 为 61ms／27ms，不是完整点击到恢复的总时长，也不是大目录性能结论；两台系统时钟不同，不跨设备直接相减。没有重新覆盖音频／视频的全部真机组合。
- 手机上以空文件夹名称触发本地校验错误，原生玻璃通知显示后自动消失，没有“知道了”模态错误弹窗，原输入弹窗可以正常取消。构建与记录在忽略的 `temp/notice-feedback/`，没有 NAS 写操作。

### 既有接续链路验证

本机回归执行实际协议、文件读写、接续管理器及页面适配方法，模拟系统分布式对象；覆盖 50,000 条目录、中文与多字节边界、短读写、路径越界、过期数据、重复/缺失条目、账号不匹配、准备失败、取消及恢复前网络失败。此类测试不能验证系统真的完成跨设备文件同步、窗口重建或媒体渲染。

媒体补修回归位于 `temp/continuation/`，另外执行实际音频管理器和页面打开方法，检查非零进度恢复、暂停优先于目标设备自动播放设置、取消／释放、旧 seekDone、传输结束后播放回调仍有效、三个媒体场景资格判断，以及完整目录后台校验不阻挡接续。50,000 条目录约 8.1 MB 的分块快照检查通过；本机耗时不能视为设备传输或渲染指标。

2026-10-23 修复包已覆盖安装到手机 `192.168.0.142:27677` 和平板 `192.168.0.154:35118`，保留应用数据。手机在 Music/1 音频、Camera 图片、Screenshots 视频页面均实测上报任务 ACTIVE，返回目录后恢复 ACTIVE；平板桌面可显示带手机标记的联文件接续图标。测试没有执行 NAS 文件修改。

重启前，实际手机→平板的冷／暖启动对照失败：目录和图片场景均在系统 `HOME/ContinuableViewModel` 报 `continueMission fail, code: 16300501`。最终包已增加不含业务数据的生命周期阶段日志，失败时源端没有 `Export requested`、目标端没有 `Receive requested`，说明该次失败发生在应用接续回调之前；手机系统另有 `distributedsched/CommAdapter` 的软总线套接字 `Permission denied` 日志。不能仅凭宽泛的系统错误码判断是应用缺少权限。

官方 DistributedSchedule 错误码将 16300501 定义为系统服务工作异常，建议稍后重试或重启设备。官方接续概述同时明确 API 12 起接续无需申请 `DISTRIBUTED_DATASYNC`，不能直接照搬旧 FAQ 的权限建议给当前 API 26 包增加授权。用户重启两台设备后，保持同一修复包与权限配置，系统入口及分布式文件传输恢复正常；未增加应用侧重启、反复发布任务或额外授权的补丁。

上述是当前两台设备和素材的真实检查，不能替代异常网络／账号、不同系统设置、PC、反向接续、视频接近末尾等完整组合。截图、原生布局和生命周期日志保存在 `temp/continuation/`；两端测试播放均在检查结束后关闭，没有 NAS 文件写操作。

后续仍需补充验证的组合：

1. 冷启动和已打开应用的接收，均无错误首页/顶栏闪现。
2. 大图库中间图片接续、连续切图、返回、父目录加载和再次打开。
3. 视频播放/暂停和接近末尾的位置，源端暂停、接收端 seek，失败时源端可继续。
4. NAS、UID 不一致、目标无权访问、NAS 断线和目录在传输后变化。
5. 两端都有传输队列时任务保持，通知点击可取消接续并打开传输页。
6. 准备/接收时取消、锁屏、切应用、超时和连续发起，旧回调不覆盖新页面。
7. 图片、视频与相册弹窗的正常打开和返回，无接续时不改变原有交互。

### 2026-10-26 接收上下文替换

用户同意合并后，确认框采用官方 `AlertDialog` 组件，与详情共用 `presentPageDialog` 管理原生弹窗 ID、关闭、取消及资源清理。接续与页面销毁会关闭所有现存弹窗，原生 ID 尚未返回时延后执行关闭；旧确认结果不能触发新页面上的文件操作。平板确认遮罩消失、正常按钮返回原索引、系统返回取消、关闭后可继续触摸；`tests/page-dialog-regression.cjs` 补充晚到 ID、打开失败与重复关闭检查。

目录刷新同时记录导航代次、路径、根类型和账号。复制／移动完成后的刷新、新建目录的晚到结果不能覆盖接续的新页面；`tests/directory-refresh-regression.cjs` 检查根目录、普通目录、账号切换及正常复制收尾。

手机重新连上后，正常包完成了手机→平板的真实接续：设置、图片、音频、视频和复制目标选择页的接收状态均可替换，恢复后的首个多选点击可用。用户提出下方播放保留策略后，两端再次安装同一正常包，补测结果见下文。

### 接续时保留已有播放

- 接续目录或图片：接收端正在播放的音乐保持同一个播放器和系统会话，只隐藏播放页；视频复用原生 PiP 小窗，继续播放。已暂停的旧播放不额外保留；不支持或无法启动 PiP 时关闭旧视频，避免盖住新页面。
- 接续音乐或视频：关闭旧播放器与系统会话，不保留额外的旧播放会话。等待旧会话清理结束后交给新媒体，避免两路声音和播控抢占。
- 音乐的系统播控入口可恢复原播放页。音乐后台恢复与视频小窗恢复共用原有的目录／排序／位置／祖先导航快照，最多保留各自现存播放器的一个来源；没有另建导航树、后台轮询或第二组媒体播放器。
- 后台音乐自动切歌沿用原播放队列，不抢占当前目录的忙碌状态。视频小窗的上／下一条也使用原视频目录。恢复播放页会撤下当前图片，返回定位仍走既有媒体返回逻辑。
- 小窗异常关闭旧视频，不重新弹出被替换的全屏视频。后台音乐的进度、系统播控和是否允许应用退后台继续播放仍由现有音频设置与后台任务控制。

平板临时验证包执行实际恢复方法，检查目录与图片接续下的音乐进度持续前进、目录可点击、系统播控入口恢复音乐原目录、视频小窗持续播放、从小窗恢复原目录，以及新音乐关闭旧小窗。验证入口已移除。`tests/continuation-playback-regression.cjs` 覆盖保留／替换策略、账号边界、小窗失败和播放列表来源；音频流式播放回归补充目录忙碌时后台切歌不会释放目录状态。

最终正常包的真实手机→平板验证通过六种组合：目录保留音乐、目录保留视频小窗、图片保留音乐、图片保留视频小窗、新音乐替换旧视频、新视频替换旧音乐。音乐和视频保留时进度继续前进，从播控／小窗恢复均回到原媒体目录，关闭媒体后的返回正常。短视频自然播完时按“非正在播放”处理，不额外保留。测试样本不足以覆盖等待过程时改用较长样本，不更改应用策略。

图库文件夹任务的原生操作菜单也曾在恢复后残留遮罩。现在保留原操作项与索引，使用官方 `CustomContentDialog` 并接入相同关闭生命周期；平板复现修复前残留、修复后关闭且下一次触摸正常，未创建或执行上传任务。音乐和视频的系统播控 WantAgent 使用不同请求编号，避免恢复入口参数互相覆盖，`tests/audio-launch-regression.cjs` 执行两种播控的实际配置方法验证。

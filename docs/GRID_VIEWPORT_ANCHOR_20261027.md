# 网格旋转与接续定位

网格密度按当前窗口的 vp 宽高计算，以约 36 张图片为一屏的目标，最多 7 列，最小缩略图宽度 80vp。手机典型为 4 列，平板竖屏 5 列、横屏 7 列；方形窗口通常为 6 列。所有网格及导航快照继续调用 `FileGridLayout`。

## 锚点规则

- 普通浏览时，保存顶栏下方首个可见行的首个**文件**及该行被遮住的比例，混合目录中的视频也可作为锚点。
- 不能到 `onAreaChange` 才读取旧位置。原生布局可能已经改变，先发生的滚动索引回调也可能来自新尺寸；采集时核对实际组件尺寸。
- 在应用新尺寸与定位之前冻结锚点，防止布局发出的滚动回调覆盖它。布局稳定后按原文件定位，不重载数据源。
- 同一次或连续多次尺寸变化继续保留原文件，不能把它在新布局中所在行的首文件替换为锚点；否则列数来回变化会逐渐取整偏移。
- 用户触摸时取消尚未执行的校正，再按实际位置采集。切换目录、排序、显示模式、媒体界面或导航代次后，旧校正无效。
- 目录开头保持滚动偏移 0。其他位置按目标窗口的行高、顶栏及遮挡比例定位，不复用源窗口像素偏移。

旋转和接续共用 `restoreGridViewport`。接续复用现有 `anchor` 文件路径，仅新增可选的 `anchorFraction`、`anchorAtStart`；不增加图片、文件树或逐图位置数据。旧端忽略新增字段，新端接收旧数据时按文件定位。媒体接续仍以当前媒体文件作为返回目标。

本次没有增加逐图片的旋转位移动画。图片打开、返回继续使用原有共享元素实现。

## 当前渲染实现（2026-10-28）

恢复原生逐文件 Grid：`LazyForEach(fileEntryDataSource)` 的键是文件路径，换列仅更新布局，保留相同文件的节点。删除 `FileGridRows`、`FileGridRowView`、行号/文件索引换算和不再使用的行缓存测试。密度规则、缓存四行、缩略图加载、沉浸控件及原有共享元素返回逻辑保留。

锚点修复只处理文件身份、被遮挡比例与有界定位，不再重载数据源。目录定位和接续继续共用同一个恢复方法；不能把目标文件取整成新行首再覆盖原锚点。

没有保留提前将网格改为竖屏尺寸的 `WINDOW_WILL_ROTATE` 路径。该路径的录屏虽然没有整块黑帧，但用户确认横屏转竖屏前出现半边空白，因此不能判为通过。窗口实际同步尺寸回调与组件尺寸回调仍共用同一入口。

## 原因与取舍

`2895824` 引入整行适配及纹理缓存后，文件随列数重新分组，行的代次和键也改变，导致换列时重建行。后续用截图、提前布局等手段补偿产生了更多问题。当前恢复逐文件节点生命周期，单独保留定位修复。按行加载、按行合批与流畅旋转并非原理上互斥，但当前行适配层未可靠兼顾，不能继续作为已完成方案保留。

失败实验留在忽略的 temp 目录，生产源码没有第二套旋转渲染器、截图拼接、逐图临时位图、额外解码缓存、强制 UI 刷新或逐帧任务。

用户确认平板当时安装的 `flat-original-control.hap` 旋转效果最好。清理包 `native-grid-clean.hap` 保持该布局与显示逻辑，仅删除无用的行适配和索引换算。

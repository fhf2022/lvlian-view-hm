# 缩略图首屏与就绪通知

2026-11-02 平板现场，目录元数据正常返回，但缩略图接口返回 HTTP 423。实际响应体为 `thumbnail is generating asynchronizely, please wait for websocket`。这是该接口的异步就绪约定；不能只按 HTTP 标准名称推断原文件被锁定，也不能从响应判断服务端已有缩略图的内部状态。原始日志、私有路径与截图仅留本机 temp。

已核对当前 NAS 网页文件管理器及桌面公共脚本：缩略图 GET 使用 `Thumb-ID`、`App-ID`、`Client-ID`；同一个客户端标识用于 `/ugreen/v1/desktop/ws?client_id=…&lang=zh-CN`。WebSocket 中 `data.event = thumbnail-done`，通过 `data.body.list[].thumb_id` 找回待显示的图片，再请求图片内容。直接返回图片只需一次 GET；异步响应后取图仍需要后续 GET。通知减少的是等待期间的无效重试，不承诺所有图片只请求一次。

`ThumbnailNotifications` 维护一个会话级连接和最多 256 个映射，鉴权复用现有会话请求头，不写入日志或连接 URL。使用官方 Network Kit WebSocket，保持证书校验。握手最多等待 2 秒，失败后有 5 秒冷却，没有自动重连轮询；下一次实际缩略图请求按需重连。心跳快照间隔 30 秒，无关系统消息在 JSON 解析前过滤。后台关闭连接，切账号重建标识，切目录/开始滑动清理旧映射。

就绪消息交给现有 `PreviewLoadQueue.retryNow()`，只唤醒已接受的任务，不自行新增任务。通知早于 HTTP 423 时合并为同一次后续请求；旧请求先释放并发名额，再重新入队。保留原有 4 并发和 256 待处理上限。所有等待共用一个队列计时器，等待不占工人。仅 423 可有限恢复：正常连接优先等待通知，15 秒没有通知才兜底；断线时按 1、2、4、8、16 秒延后，单任务最多 5 次恢复。其他 HTTP 状态不接入此恢复策略。

列表和网格在提交渲染帧后共用现有 `flushPendingVisibleLoads()`，先补齐真实可见项、刷新已就绪却未显示的单元，再做有界邻近预热。目录转场结束保留属于当前目录的可见记录、范围及已绘制 URI，清除旧目录记录；移除继承的旧滚动标志。真正的新滑动、时间轴定位、查看器打开和过期 generation 仍阻止补加载。音频、视频封面也沿用相同首屏扫描。瀑布流保留原分组与原图任务，不接入列表预热。

原图走现有下载描述符及 HTTP/Range 下载，不接入缩略图就绪通知；原图断点续传、缓存键、淘汰和解码策略保持原样。

验证包括生产方法的主机回归（首屏补齐、缓存刷新、通知去重/早到、取消、账号隔离、连接超时与并发上限）及平板真实通知。一次本地未缓存目录中，23 个 423 分别收到就绪通知，随后全部显示，完成早于 15 秒兜底。该记录验证通知链路，不代表所有固件、网络和媒体类型均已验收，也不是帧率对照结论。

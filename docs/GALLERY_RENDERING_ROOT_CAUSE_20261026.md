# 平板与系统图库：滑动差距的受控排查

后续完整交互接入、当前保留实现与测试结果见 [按行缓存接入与验收（2026-10-27）](GALLERY_ROW_CACHE_INTEGRATION_20261027.md)。下文“恢复基线”描述的是此前研究阶段的状态。

2026-10-26，基线 `eb029e7`。本轮在用户要求“先搞清楚原因再改”后停止推广组件改造，改做显示密度、图片源和渲染阶段对照。生产代码及平板最终恢复原基线；十列、渐变模糊、独立沉浸光感按钮、底栏、时间轴和动画设计均保留。

## 已确认的结论

**显示密度解释了很大一部分差距；继续加缓存或逐张改纹理格式，收益仍有限。真正减少渲染单元的整行绘制隔离原型，在十列和原有材质下测到约 119 次刷新/秒。** 这一原型简化了逐项交互，是后续改造方向的上限验证，不是可发布优化。第 1～5 节记录早期定位，第 6～7 节记录继续验证及最新结论。

控制为六列时，主要剩余差距在图像绘制和合成阶段；十列下逐项创建、布局和绘制的组织也仍有成本。不能把“只改组件复用收益不够”进一步误推为所有主线程优化无用，也不能将独立玻璃控件的数量当作无法达到高刷的硬上限。

系统图库的完整私有实现不可见。以下将真机观察、受控测量、公开接口能力与推断分开，避免把推测写成源码事实。

## 对照条件

- 同一台 PCE-W30，2880×1920、120 Hz，API 26。
- 联文件 Camera 图片目录；系统图库隐藏侧栏，固定“日”视图。两者网格视口均为 `[0,86][2880,1920]`。
- 原版联文件横屏十列，约 70 个屏内单元；图库日视图六列，约 24～30 张。诊断包只将联文件改成六列，其他实现、材质、图片来源及缓存行数保持基线。
- 手指移动 1400 px，速度为 1600 / 3200 / 6400 px/s，三次向前、三次回滑循环。SmartPerf 每档采样 15 个窗口，去掉首窗，统计其余 14 窗。
- 采帧率时不截图、不查布局、不并行采集 trace。独立 trace 使用六次完整手势、松手后间隔 1 秒；各份均核对完整 DOWN/UP。
- 两应用的具体素材仍不相同，滚动惯性和缓存状态也未完全统一。因此不能把均值差换算成某个因素的精确贡献百分比。

这里的刷新次数来自应用 Surface 统计，不等同于逐帧验证物理屏幕呈现 FPS。UI 主线程耗时和 Render Service 阶段耗时单独报告，不能相加或取倒数冒充帧率。

## 1. 先排除显示密度混淆

| 场景 | 慢速刷新次数/秒 | 中速 | 快速 |
| --- | ---: | ---: | ---: |
| 联文件原版，十列 | 74.50 | 72.43 | 63.50 |
| 联文件，仅诊断时改为六列 | 103.86 | 101.93 | 94.93 |
| 系统图库，全宽、固定日视图六列 | 118.93 | 119.71 | 119.86 |

十列变六列会减少屏内和预加载区节点，并减少每帧实际绘制的图片。即使单格尺寸更大，刷新次数仍明显提高。这证明先前直接用十列对六列比较，会夸大组件实现本身的差距。**六列仅用于诊断，不作为设计修改。**

图库“月”视图在组件树中常把许多可见小图组织为少数大块 `CachedImage`；“日”视图则可看到逐张的 `CachedImage`。月视图不能按视觉上小图的数量，与逐张 `Image` 单元直接对比。

采样中还发现，重新 `aa start` 拉起图库可能恢复到月视图。误标为 `gallery-fullwidth-day-*` 的那组实际为月视图，**作废，不纳入上表**。后续 `gallery-fixed-day-*` 不重新启动图库，并在采样前及每档结束检查 `dayGrid` 仍存在。

## 2. 等密度以后，主线程不是主要剩余差距

| 高速独立 trace | UI 活跃滚动帧 P95 | RS RenderFrame P50 / P95 | RS PostAndWait P50 |
| --- | ---: | ---: | ---: |
| 联文件原版十列 | 10.41 ms | 13.75 / 17.02 ms | 8.63 ms |
| 联文件诊断六列 | 5.14 ms | 9.61 / 12.92 ms | 6.04 ms |
| 系统图库全宽日视图六列 | 6.54 ms | 7.33 / 10.11 ms | 0.69 ms |

同为六列时，联文件 UI 主线程 P95 已低于图库，但刷新次数仍低，RS 渲染及等待更重。`PostAndWait` 是并行渲染的等待阶段，不能把它当作一段可独立相加的 JS 工作，也不能据此直接给所有成本分配百分比。它与 RenderFrame、Surface 刷新统计共同表明：只优化组件创建或减少状态装饰器，无法解决当前全部差距。

## 3. 相同材质外观，合成区域组织仍有区别

从实际 `RSFilterCacheManager::TakeSnapshot` 事件统计：

- 联文件十列约 **9 个取样区域/渲染帧**：顶部渐变、返回、多选、搜索、底部三个控件、上传悬浮按钮、时间轴。
- 联文件六列仍约 **8.87 个/帧**，密度调整没有同时删掉材质。
- 全宽图库日视图约 **4.91 个/帧**：顶部渐变、一个覆盖顶栏菜单范围的取样区域、侧栏切换按钮、底部两个控件。

图库确实也有沉浸光感和渐变模糊，不能把流畅度简单解释为它没有材质。这里确认的是区域组织与每帧工作量不同。联文件包含额外的时间轴与上传按钮，不能通过删功能或改成整块均匀模糊来消除差异。

GPU render pass 中位数约为联文件 45、图库 42。这个计数不能独自解释整段性能差距，也不能将九个区域直接等同于九次完整画面重绘。滤镜区域统计是后续分析绘制合并的依据，不是关闭沉浸光感的理由。

## 4. 多图资源处理有可分离的成本

另做十列诊断，保留原始单元层级、尺寸和全部材质：

| 十列诊断 | 慢速刷新次数/秒 | 快速 |
| --- | ---: | ---: |
| 真实多图，仅停掉完成/错误业务回调 | 76.57 | 61.71 |
| 所有格复用同一已缓存 URI，同时停掉相同业务回调 | 86.43 | 76.86 |

后一组仍计算每项原来的显示状态，最后仅覆盖交给原生 Image 的 URI。停掉完成回调是为了防止同一测试图片的尺寸被记入其他真实文件的元数据；前一组使用相同空回调，作为混淆因素的控制。没有上传或修改 NAS 文件。

单独取消业务回调没有明显收益；共享同一资源后则有提升。该结果支持多图解码、原生资源加载、纹理上传/复用这条路径具有实际成本，不能只把“磁盘缩略图已命中”视为整个绘制缓存已经命中。仍需继续区分这些阶段，不能凭此声称纹理压缩一定能提高某个固定比例。

共享 URI 的独立 trace 中，UI P95 为 9.37 ms、RS RenderFrame P50 为 12.79 ms；原版十列分别为 10.41 / 13.75 ms。它没有消除原来较重的合成工作，所以共享资源本身也没有达到系统图库水平。

## 5. 系统接口能力与公开替代路径

真机树中的图库图片标签为 `CachedImage`。官方文档明确存在系统级 `MediaCachedImage`，支持 `ASTCResource` 纹理拼接（纹理 URI 数组和列数），且该能力仅供系统应用使用。开源 JS 桥也区分 `ASTCResource` 与普通 Image 资源，不能把这一组件简单理解为在普通 Image 上加一个缓存开关。[系统 API 文档](https://github.com/openharmony/docs/blob/master/en/application-dev/reference/apis-arkui/arkui-ts/ts-basic-components-mediacachedimage-sys.md)、[JS 桥源码](https://github.com/openharmony/arkui_ace_engine/blob/master/frameworks/bridge/declarative_frontend/jsview/js_cached_image.cpp)。

图库 GPU 资源记录中存在约一字节/像素的估算；这与压缩纹理特征相符，但尚未取得足以排除其他格式的明确 format 记录。**不能仅凭标签、资源大小或公开接口，就断言每张图库图片都使用 ASTC，也不能宣称已还原华为图库全部私有实现。**

本机公开 SDK 的 Image Kit 支持 `ASTC_4x4` 显示格式、`image/sdr_astc_4x4` 编码，SDK 说明其存储占用约为 RGBA_8888 的四分之一。后续真机已验证普通应用可转码并显示 NAS 缩略图，但收益不足以直接接入正式链路，详见第 6 节。这里的“四分之一”是相对 RGBA 像素的存储量，不是相对 JPEG 文件的大小。

## 6. 继续验证：压缩纹理、解码缓存和共享图集

继续使用同一台平板、十列、同一 Camera 目录，保留渐变模糊、所有独立沉浸光感控件及原始 Grid/LazyForEach。临时诊断包通过 Want 参数切换，数据来自已缓存缩略图，没有向 NAS 上传、修改文件或清空应用数据。每档仍使用 1400 px、三前三后连续手势、15 窗去首窗的方法；采帧和 trace 分开进行。

纹理准备完成、停止转码并重新启动应用后才测滚动，不把后台转码的消耗混入热滚动统计。各模式进入目录后用相同的六次手势预热。选择了最近的 900 个已缓存 Camera 缩略图；开始时可见 60 项中覆盖 58 项，未覆盖项回退原 URI。覆盖核对基于文件名，未逐个记录测量过程中实际提交到 GPU 的纹理身份。没有把这一实验包装成网络冷加载加速。

| 十列场景 | 慢速刷新/秒 | 中速 | 快速 | 快速帧间隔 P95 |
| --- | ---: | ---: | ---: | ---: |
| 原缩略图，诊断对照 A | 76.00 | 71.36 | 63.14 | 24.96 ms |
| 每张单独生成 ASTC，再交给原 Image | 80.21 | 75.00 | 67.50 | 16.80 ms |
| 原缩略图，生命周期内设置解码缓存 128 张 | 77.00 | 68.64 | 60.57 | 25.00 ms |
| 十张共享一张 ASTC 图集，单元裁切显示 | 82.50 | 78.21 | 69.07 | 24.92 ms |
| 恢复原资源，对照 B 复测 | — | — | 63.64 | 24.94 ms |

这些仍是应用 Surface 刷新统计。单次小幅变化没有重复到足以承诺固定收益；原版快速复测与首次对照接近。长帧仍存在：图集组快速采样最大间隔约 249 ms，原资源复测也有约 333 ms 的间隔，因此不能声称图集解决了卡顿，也不能把长帧单独归咎于图集。

### ASTC 的收益和代价

- 900 张均成功用公开 Image Kit 解码、编码为 `image/sdr_astc_4x4`（quality=85）。原缩略图合计 **33.04 MiB**，逐张 ASTC 合计 **237.39 MiB**，约为原文件的 **7.19 倍**。
- 全样本串行调用，解码时间累计约 17.38 秒，编码约 83.43 秒；单张解码加编码中位数约 99 ms。此值包含当前设备运行条件，不是纯算法计时，也不包含全部文件 I/O。首批 30 张的编码中位数约 28 ms，不能拿首批值代表完整批次。
- 各模式预热后的进程内存快照中，原资源 GL+Graph 约 102.4 MiB，逐张 ASTC 约 47.4 MiB，图集约 58.5 MiB；总 PSS 约 331 / 305 / 280 MiB。这是一次静止快照，不能称为峰值内存或稳定驻留量。
- ASTC 的显存优势有证据，热滚动收益较小。若接入，还需新增编码时机、容量、过期回收、旋转及透明度验证，不能仅凭省显存就接受七倍文件增量和额外编码负担。本轮未接入。

独立快速 trace 中，逐张 ASTC 的 UI 活跃帧 P95 约 10.20 ms，RS RenderFrame P50/P95 约 13.23/16.85 ms，PostAndWait P50 约 8.37 ms；图集分别约 9.42、13.07/16.32、8.36 ms。原版此前同类数据约 10.41、13.75/17.02、8.63 ms。资源变化没有消除较重的合成与等待阶段。

### 解码缓存不是这次的大收益点

官方 `UIContext.setImageCacheCount` 支持限制解码后图片缓存数量，说明未设置时默认 0，且**仅在 @Entry 页面的 onPageShow/aboutToAppear 中调用才生效**。[官方接口文档](https://github.com/openharmony/docs/blob/master/en/application-dev/reference/apis-arkui/arkts-apis-uicontext-uicontext.md#setimagecachecount23)

最初 `texture-cache128` 在 Ability.loadContent 回调调用，未遵循该生命周期限制，**该组作废，不作为“开启缓存无收益”的证据**。随后 `cache-lifecycle.hap` 在 Index.aboutToAppear 内读取 Want 指定的 128 并调用本页 UIContext，重新进入目录及预热，再测三档。表中采用的是正确生命周期的 `texture-cache128-valid`；本轮仍未测到滑动提升，未保留设置。修正已向用户说明，不隐去前一组测法的问题。

**默认 0 不等于整个原生图像链路完全没有缓存，也不等于每帧都重新从磁盘解码。** 开源 ImageCache 还区分 ImageData、ImageObject 和绘制图像等缓存，不能把一个容量参数当成所有层的总开关。[缓存结构源码](https://github.com/openharmony/arkui_ace_engine/blob/master/frameworks/core/image/image_cache.h)

### 共享纹理不等于真正合批绘制

诊断图集每十张生成一张 2840×284 的 ASTC，保留原十列及每项 Image，通过放大源区域和裁切显示对应图片，截图核对内容及位置。为避免把图集尺寸写入单张图片元数据，图集分支不调用原单图完成回调；这不是完整的生产等价替换。前一轮单独停业务完成回调未测到收益，仍需保留这一混淆说明。

这个实验减少独立图片资源，**没有减少原生 Image 节点与实际图片绘制次数**，也不是系统 MediaCachedImage 的完整实现。结果说明共享纹理本身不足以对齐图库；不能据此断言真正的批量绘制没有价值。源码仅封存在 temp，旋转、共享元素动画及缓存失效没有作为图集生产方案验收，不能发布。

### 补查调度频率

另以相同快速手势，用 SmartPerf 同时采集 CPU/GPU/温度；图库固定全宽日视图并在前后验证。联文件刷新约 65.71/秒，图库约 115.21/秒；GPU 频率均值约 488 / 551 MHz，进程 CPU 使用率约 13.57% / 6.14%。联文件大核频率均值约 2.12 GHz，图库对应核约 1.92 / 1.83 GHz。

这是不同密度、不同素材的短时间采样，温控和采样顺序未完全控制。它显示运行频率确有差异，但**不能证明存在应用白名单，也不能把全部差距归因于调度**。不通过循环性能提示或强锁频掩盖渲染成本。官方 perfHint 还有持续时间及调用间隔约束，不适合作为任意长时间滚动的强制提频开关。

补充核对：图集 trace 末尾 Grid 上边界为 78 px，而早期样本为 86 px，系统状态栏避让有 8 px 的变化。布局始终为十列，不能将这些实验称为所有系统状态完全一致的实验室测量。

## 7. 区分共享资源和真正减少绘制单元

在上一实验之后继续制作 `row-probe.hap`。同样的 900 张现有缩略图，每十张离屏预合成为带单元间距的 ASTC；Camera 内每行改为一个 GridItem+Image。原十列的视觉密度、顶部渐变、返回/多选/搜索、底部三处玻璃、上传按钮及时间轴仍由原页面提供。没有关闭沉浸光感或把按钮改成整块背景。

**这份原型不包含逐张点击、长按、多选、单图可见事件、共享元素锚点与按单文件定位。** 素材按诊断清单分组，次序也不保证等于真实目录的排序。因此它是合并绘制/减少节点的联合上限实验，不能把全部差值归因于某一个 GPU draw call，更不能将结果称为完整功能下的发布帧率。全量离屏准备耗时约 50.35 秒，也是生产方案不能照搬的部分。

| 同一十列场景 | 慢速刷新/秒 | 中速 | 快速 | 快速帧间隔 P95 |
| --- | ---: | ---: | ---: | ---: |
| 整行绘制隔离原型 | 114.50 | 105.14 | **118.57** | **8.35 ms** |
| 同一个诊断 HAP 切回普通完整网格复测 | — | — | **63.71** | 24.96 ms |

快速组去首窗后 14 个窗口为 117～120，最大间隔约 16.71 ms，未记录到超过 33.33 ms 的间隔。中速组原始窗口有 1 和 69 等低值，未事后剔除，均值仍按相同规则为 105.14；尚未定位这些短暂异常，不能把中速写成稳定 120。原型测试期间平板已接电，后面的普通网格对照紧随其后，在相同当前设备状态下仍约 63.71。

独立快速 trace 的完整六次手势已验证，UI 活跃帧 P50/P95 约 **1.79/3.50 ms**，RS RenderFrame P50/P95 约 **8.10/9.98 ms**，PostAndWait P50 约 **4.87 ms**。与此前约 10.41 ms 的 UI P95、13.75 ms 的 RS RenderFrame 中位数相比，两端工作都下降，不能只把收益描述成显存节约。

取样记录中仍存在原来的九类材质区域，共 7986 次 TakeSnapshot / 932 次 RenderFrame，平均约 **8.57 次/帧**。这说明保留这些控件的外观时也可以进入高刷新路径，不能继续把“九处玻璃”本身当成必须改设计的理由。Native Image 节点统计从普通组约 60～80 量级降至约 10（包含界面其他 Image），与真正减少渲染单元相符。

这**不证明系统图库日视图采用了同一套按行实现**；图库私有实现仍不可见。它提供的是普通应用可以复现的大收益方向：把大量单项的构建、测量、图片命令提交成批组织，而不是单纯替换文件后缀或扩大缓存。

整行 trace 首次接收超过脚本的 30 秒文件传输限制，产生不完整本地文件。之后从已结束的远端 trace 重新完整接收（115073841 字节），再重新分析，确认六次手势完整。正式数据采用完整文件；不能采用前缀文件的阶段统计。

## 下一步的实现边界

逐张压缩纹理、解码缓存开关、仅共享图集，暂时都不值得作为正式优化合入。整行绘制的隔离原型已证明显著潜力，下一步才是将**批量绘制层与现有单图交互/动画逻辑衔接**，保留原数据、返回定位与动画时序作为唯一来源。

生产实现不能全相册预转码后才显示；必须只处理可见及有限缓冲行，原缩略图先正常显示、批绘制未就绪时回退，滚动/看图优先，限制解码编码与磁盘内存预算。排序、列数、账号、文件版本变化都应能失效。进入或返回查看器时，涉及的行要与原独立 Image 锚点配合，沿用已经调好的隐藏、布局和飞回时序；多选、搜索、旋转与首划都需重新验收。不能将当前无交互的原型直接塞进正式网格。

当前还未实现这一完整功能方案，也未还原系统图库的完整私有实现，不能承诺生产十列稳定 120 帧。

原始十列、独立玻璃按钮和标准渐变外观继续保留。不会用减少列数、关闭材质、增加无界缓存或长期后台转码来冒充本次优化完成。

`Repeat`、属性级更新和单元绘制缓存的组合曾测到约 82.5 / 78.7 / 69.8 次每秒，但独立高速 trace 的 UI P95 上升至 13.43 ms，没有解决主要瓶颈。该前端候选及通过的回归测试已保存至 `temp/perf-rootcause-20261026/candidate-source/`、`candidate-tests/`，未作为本轮正式代码保留。不能把约一成的局部收益当作已经对齐系统图库。

最终源码、测试和构建输出恢复基线；平板覆盖安装已保存的正常包，保留应用数据。未推送 GitHub，未变更版本或正式发布包。

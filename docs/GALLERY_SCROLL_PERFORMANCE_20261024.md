# 平板图片目录纵向滚动性能研究（2026-10-24）

范围仅为图片目录网格的正常上下滚动。目录横向转场、图片查看器左右翻页、NAS 下载效率均不在本轮调整范围内。初始基线为 `3dd92be`；本轮保留按需获取网格位置、稳定时间轴刻度，以及减少缩略图重复求值和隔离网格展示层的修改，不涉及发布包变更。仅复用内层图片组件、增加解码缓存与强制显示缓存项的试验均已撤回。

最终三档仍为 1400 px、三次向前与三次回滑、手势间隔 1.0 s，均核对六次完整 DOWN/UP。UI 主线程滚动帧 P95 为 **6.78 / 6.72 / 9.53 ms**；匹配该手势间隔的原始对照为 **10.17 / 13.93 / 26.11 ms**。这些是调试包 trace 的主线程工作耗时，不能换算为屏幕呈现 FPS。高速仍有 30 / 931 个滚动帧超过 16.67 ms，最大 30.18 ms，尚未消除全部长帧。

## 设备和方法

- 平板 `PCE-W30`，API 26，系统 `7.0.0.111(SP8C00E111R1P2)`；分辨率 2880×1920，采样时屏幕模式为 120 Hz。
- 当前 Camera 图片目录，网格为 10 列。原生 trace 显示 `cachedCount(4)` 对应每侧 40 项，并非每侧 4 张。
- 每档手指移动 1400 物理像素，从 y=1650 到 y=250，约四分之三屏；x=1100，避开时间轴和浮动工具栏。每档连续向下浏览三次，再反向回滑三次。
- 注入速度分别为 1600、3200、6400 px/s；它们是手势速度，不能当成容器的惯性滚动速度。
- 采样时不抓屏、不查询布局。三份正式样本都核对到完整的六次 DOWN 和六次 UP；早期缓冲区不够完整的记录不纳入结果。
- 从应用主线程 `OnVsyncEvent` 中筛选包含 Grid 滚动处理的帧，排除静止帧，并按 DOWN/UP 分别统计手指滑动和松手后滚动。

## 结果

下表是 **UI 主线程一次 VSync 工作的墙钟耗时**，不是屏幕实际呈现 FPS，也不是端到端输入延迟。采样包含调试包及 tracing 的开销；120 Hz 的单帧时间约为 8.33 ms。

| 注入手势速度 | 有效滚动帧数 | P95 | 最大值 | 超过 16.67 ms |
| --- | ---: | ---: | ---: | ---: |
| 1600 px/s | 1065 | 9.94 ms | 39.35 ms | 44 / 1065（4.1%） |
| 3200 px/s | 633 | 27.57 ms | 40.94 ms | 55 / 633（8.7%） |
| 6400 px/s | 254 | 30.86 ms | 55.05 ms | 74 / 254（29.1%） |

手指仍接触屏幕时，三档 P95 分别为 10.37 / 29.76 / 30.31 ms；松手后分别为 9.07 / 21.21 / 31.88 ms。高速样本向前浏览 P95 为 32.48 ms，回滑仍为 29.23 ms，不能把卡顿只解释为首次下载。

这些是每档一次的真实样本，顺序采样中的图片内容、内存缓存及温度未完全固定，不能据此宣称精确性能增益。另做的高速基线对照从重新进入 Camera 开始，P95 为 31.39 ms、最大 57.65 ms，与上述高速样本同量级。

## 已定位的工作

1. **新网格单元创建和销毁。** 高速样本最慢的 55.05 ms UI 帧中，`Builder:BuildLazyItem` 合计 self wall time 约 16.99 ms，另有单元生命周期、Grid 测量及布局。在另一帧也有约 14.47 ms 的单元创建。这是可直接对应到主线程长帧的证据，不能只归因于图片解码。
2. **大量位置回调。** Grid 的缓存区和可见区一起参与区域变化检查。高速样本 `HandleOnAreaChangeEvent` P50 3.69 ms、P95 4.53 ms，最大 8.82 ms。代码为缩略图共享元素和多选命中记录逐项全局坐标；即使条目尺寸不变，滚动导致的位置变化也会触发。仅在回调开头加判断，不能消除框架的遍历及 JS 回调成本。
3. **时间轴刻度重建。** 高速样本有 24 次 `FisheyeTimeline` 更新，单次 P50 7.89 ms、P95 9.15 ms。其刻度 key 包含随焦点时间变化的 `frameKey`，跨日期时会引起一批节点替换，叠加在网格滑动上。不能把这部分成本当成 Grid 的纯布局算法成本。
4. **本地缩略图重复解码仍存在。** 高速样本有 596 次 `CreateImagePixelMap`，单次 P95 16.47 ms。它们包含工作线程事件，不能把其累计耗时直接加到主线程，也不能据此断言每一次解码都造成掉帧。此前管理记录中 fixed-source、Blank、解码尺寸回退等结论继续有效：磁盘命中不等于已解码图复用；不应直接固定成方形小图或盲目增加缓存行数。

## 建议的验证顺序

先做小改动的单变量验证，每次沿用上述三个速度、距离及前进/回滑方法。

1. **有界解码缓存对照（已完成）。** API 23 起 `UIContext.setImageCacheCount` 可控制解码图片缓存。当前代码没有显式设置；SDK 声明及官方 FAQ 说明该项默认不缓存。补测仅增加 `setImageCacheCount(64)`，结果见下节：没有解决高速长帧，暂不纳入生产。该接口按数量而非字节限制；其他容量也需单独验证内存、原图查看、账号切换和缓存失效，不能仅凭接口存在就全局启用。
2. **减少每帧逐项全局坐标采集。** 优先验证规则网格的静态尺寸和相对位置复用，通过容器滚动量推导位置；点击打开、返回和多选拖选时再核对必要项。保留共享元素返回定位和首划行为。瀑布流有变高条目，不应直接套用规则网格公式。
3. **稳定时间轴刻度节点。** 复用刻度身份，仅更新日期、坐标和样式，避免跨日期重建整组；保留玻璃宿主及效果留白，不用修改外壳来换取帧率。
4. **最后验证单元复用和创建削峰。** 对纯缩略图展示层尝试复用／预创建预算，检查复用后旧文件身份、进度、旋转、选中态和共享元素是否残留。现有代码曾因抽取 Builder 破坏过场动画，不能直接替换整个文件单元或引入另一套图库组件。

本轮没有拿同一组素材、相同密度对系统图库做严格 A/B，也未分析其闭源源码。官方图库可作为流畅度目标，具体实现依据应来自实际 trace 和公开 API。官方推荐的懒加载、复用、缓存策略需要结合本项目已有返回动画验证，不能机械替换。

### 从 trace 确认的实现差别

1. **位置检查范围很小。** 图库三档 `HandleOnAreaChangeEvent_nodeCount` 始终为 10，高速回调阶段 P50 / P95 / 最大为 0.017 / 0.023 / 0.094 ms；联文件高速基线注册节点中位数 145、P95 为 155、最大 175，对应阶段 P50 / P95 / 最大为 3.545 / 4.404 / 6.065 ms。这是同名框架阶段的直接证据，包含检查与回调成本；不能将全部耗时精确归到某一行 JS。联文件当前逐格同时记录共享元素位置与多选命中位置，适合先验证减少常态滚动中的逐项回调，保留点击、返回及拖选所需的可靠定位。
2. **图库确实复用了图片单元。** 三档分别出现 132 / 150 / 252 次 `CustomNode:BuildRecycle [ImageGridItemView]`，复用类型为 `TimelinePageNewImageGridItemImageNode`，并有配套回收与 `CachedImage LoadData, type:OnReuse`。联文件高速基线没有该类复用事件，现有 `GridThumbCell` 也仅标记 `@Component`。图库高速单次 BuildRecycle P95 为 1.743 ms；它通常嵌套在 BuildLazyItem 内，不能把二者相加，事件数量也不能直接换算复用率。联文件的关键问题是进入新行时一批单元创建集中在同帧，需在局部图片展示层验证复用，并核对文件身份及动画状态。
3. **图片复用入口轻，但不能反推缓存细节。** 图库高速 252 次 `CachedImage LoadData, type:OnReuse` 的调用 P95 为 0.177 ms，有相应加载成功事件。本次没有捕获到与普通 ArkUI Image 同名的 CreateImagePixelMap 事件，不能因此声称图库没有解码，也不能比较它与联文件的“解码次数”。可借鉴的是展示单元和资源身份稳定、复用时只切换必要数据；图库缓存容量、图片尺寸和底层加载策略仍未知。
4. **联文件时间轴有独立长任务。** 联文件高速基线有 23 次 FisheyeTimeline 更新，P95 为 8.804 ms；代码中的刻度 key 随 focusTime 所在区间改变，会替换一批节点。图库采用另一套时间栏，没有同名组件，不能把差异全部归给某一种时间轴设计。对联文件可先稳定刻度身份、降低重复测量，不改玻璃材质及裁切留白。

建议顺序继续是：减少常态逐项位置回调 → 稳定时间轴刻度 → 局部单元复用；解码资源复用作为后续独立实验。每步仍在联文件现有 10 列场景验证，同步回归打开/返回定位、多选拖选与反向快滑。没有依据要求换容器、改少列数、直接复制系统 CachedImage，或全局增加缓存。

## 缓存对照补测

用户确认系统隐私声明后，完成两组各三档速度的对照。两组都是当前 1.0.11 的调试构建，同一源码、图片目录、1400 px 距离，每次重新进入目录，从相同起点开始；临时包只在 `aboutToAppear` 增加 `setImageCacheCount(64)`，不改变布局、缓存行数、图片尺寸、手势或下载调度。每份 trace 均包含六次完整手势。

| 手势速度 | 基线 UI P95 | 64 项缓存 UI P95 | 基线 / 缓存解码次数 |
| --- | ---: | ---: | ---: |
| 1600 px/s | 10.73 ms | 10.31 ms | 324 / 311 |
| 3200 px/s | 22.72 ms | 20.42 ms | 345 / 320 |
| 6400 px/s | 29.33 ms | 29.30 ms | 589 / 596 |

高速回滑 P95 也没有改善（28.54 → 29.18 ms）。区域回调 P95 仍为 4.40 / 4.31 ms，时间轴更新 P95 仍为 8.80 / 9.09 ms。中速、快速样本有少量差异，但单次每档的试验无法排除运行波动；不能据此证明稳定增益。

采样后的 PSS：基线三档为 288.2 / 378.8 / 308.2 MiB，缓存组为 367.8 / 332.1 / 279.5 MiB；DMA 约为 99～111 MiB。它们是采样后快照，包含堆和系统资源状态差异，不是峰值，PSS 与 DMA 不应相加，也不能把两组的全部差值归因于缓存。

结论仅限本次 64 项配置：它没有解决高速滚动的尾部卡顿，不值得直接上线。不能扩大为“所有解码缓存无用”；缓存容量和内存代价的其他组合未验证。下一步优先对逐项位置采集、时间轴刻度重建或单元创建做一次一个变量的实验。

## 第三项：图片单元创建和状态求值

### 未保留的方案

第一种单变量试验仅给现有 `GridThumbCell` 增加 `@Reusable`，在 `aboutToReuse` 更新普通桥接参数、索引并清空借用显示状态；`@ObjectLink entry` 由框架自动重绑，没有手工赋值。该方案没有替换外层 GridItem/Stack/Column，也没有改图片布局或 sourceSize。

高速 trace 实际出现 600 次 `BuildRecycle [GridThumbCell]`，证明并非“没有生效”。单次 BuildLazyItem 中位数 0.971 → 0.719 ms，但整帧 P95 10.62 → 10.37 ms，P99 24.50 → 26.78 ms、最大 30.67 → 42.27 ms，没有证明稳定的整页收益。最慢帧仍包含外层条目批量创建，另有未进一步归因的 JS 重算长任务。移动范围和运行波动尚未严格匹配，不能据此断言复用必然导致退化；本轮不值得直接保留这段行为变化。

已撤回 @Reusable/aboutToReuse 改动。试验源码、HAP 和 trace 留在 `temp/perf-gallery/reuse-leaf-trial-index.ets`、`reuse-leaf-trial.hap`、`reuse-probe-6400.*`，不进入发布。

另试验只将 `cachedCount(4)` 改为 `cachedCount(4, true)`，不改变缓存行数、下载调度和解码尺寸。高速 UI P95 从约 10.13 升到 24.32 ms，超过 16.67 ms 的滚动帧从 30 增到 71；这一组没有支持保留的收益，已恢复单参数调用。证据为 `show-cache-6400.*` 和 `show-cache-trial-index.ets`。这不等于证明所有预加载无效，也没有关闭项目原有预加载。

### 保留的重复求值优化

`GridThumbCell` 原先每个 Image 属性都调用完整 `thumbState()`，普通图片分支每次构建约 7 次，带 sourceSize 的分支约 9 次。现在保留条件分支所需的求值，并在 `Image(source)` 开头解析完整状态，随后尺寸、方向、共享元素 id、同步加载和可见性从同一个结果读取；普通分支的完整求值减少为 3 次。

该改动没有跨帧缓存，也不以生命周期钩子清空状态。已检查 ArkTS 编译结果：`Image.create` 与后续属性位于同一个原生节点更新回调，source 求值仍读取完整的当前依赖。正式测试 `tests/grid-thumb-update-regression.cjs` 直接执行生成的更新回调，覆盖仅 URI、旋转、过渡 id、隐藏状态、同步标志及尺寸变化、PixelMap 交接和占位图变为就绪图片。没有用只在初次构建执行的 `onDidBuild` 模拟更新生命周期。

同时在 `cellBuild` 诊断探针外层增加开关判断，关闭探针时不再格式化每格日志参数、额外读取无关的全局 UI 状态。其他诊断入口不在本次批量清理。

单独对照的高速 UI P95 约为 10.62 → 10.13 ms，条目构建中位数约 0.971 → 0.844 ms；单次运行波动和图片序列仍存在，不能把全部差值精确归因于这一行优化。证据为 `state-once-6400.*`、`probe-guard-6400.*` 及编译更新回归。

### 保留的小型网格展示组件

Hiperf 采样出现状态依赖清理相关热点，包括 `purgeDependencyOnElmtId`、`purgeDependenciesForElmtId`。生成的 Index 类在清理原生节点时遍历约 267 个状态变量；部分清理发生在 VSync 之间，不能只看 VSync 内的条目创建时间。采样百分比的线程分母未进一步验证，因此本报告不声称某个函数占主线程固定比例。

`FileGridCell.ets` 接管原有 Stack / Column 包装、文件夹名称、选择角标容器及触摸回调，让这些频繁创建和删除的节点属于一个只有 4 个观察属性的小组件。文件操作、多选范围算法、图片状态解析、视频进度和共享元素逻辑继续调用原有实现。可见性回调通过数据源已有的 path→index Map 读取当前索引。普通图片不再创建 Index 所属的视频状态占位分支。

图片分支通过标准 `@Builder` 传入稳定的 FileEntry 和 index，没有传入每次新建的 GridImageState 对象；移除了已经无调用的旧 `GridItemThumbnail` 入口，没有保留第二套网格界面。首次试验的内联 BuilderParam 未被编译器转换为 UI，曾导致内容未显示，立即恢复稳定包后改用标准 Builder；最终 HAP 已验证真实内容和交互，不能仅凭编译通过判断这类抽取正确。

没有给新组件添加 `@Reusable`，避免 Builder 闭包在复用后继续捕获旧条目。实际表现的收益有限，采用交替覆盖安装补测：

| --- | --- | ---: | ---: |
| B1 | 小型展示组件 | 68.86 / s | 24.936 ms |
| A1 | 仅重复求值优化 | 65.00 / s | 24.942 ms |
| B2 | 小型展示组件 | 68.43 / s | 24.906 ms |

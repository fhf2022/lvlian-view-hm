# 瀑布流原图加载窗口（2026-10-25）

加载按 12 张一组、连续最多三组组织，优先当前可见项，再预取相邻组。界面仍是原有 SLIDING_WINDOW + LazyForEach，不引入 WaterFlow 分组，不改文件身份或返回定位。

- 原图下载至已有账号/文件版本缓存，按列宽解码；不一次解码整组。
- 下载最多两张并行（移动网络最多一张，原有自动加载许可继续生效），解码最多一张。
- 滚动时暂停新下载与解码；窗口移动后中止远处 HTTP，实际请求退出才归还槽位。已完成文件仍留磁盘缓存。
- 极短横图导致可见项跨越三组时，组大小以 12 为基础倍增，确保可见项全部有加载资格；常规窗口最多 36 张。栅格组件和 PixelMap 的既有 48 MiB LRU 独立约束内存，不把“36 个压缩文件”等同于“36 张原分辨率位图”。
- Viewer 打开前暂停瀑布流预取，选中原图复用正在完成的下载，避免相同缓存文件出现两个写入者。
- Image 完成/报错、组件离屏都不再提前释放解码槽位；目录重置也等待实际解码退出。

验证：waterfall-original-regression 覆盖分组边界、超宽可见范围、实际并发、取消和重进、账号变更、Viewer 提升、磁盘回收、拒绝加载时不循环重试。Viewer 预取、共享返回和旋转返回回归通过。调试构建成功。

平板 PCE-W30 在 Photos/Camera 使用 1170px 长距离、900/1600/2800 px/s 三档滑动及反向滑动；停稳可见占位全部补齐。大图打开返回后可继续滑动。未做缓存条件一致的 A/B 帧率对照，不能据此量化帧率收益。

补充收尾：实际 decoder 回归复现了“解码未完成时进入时间轴拖动/大图，迟到结果仍提交”的问题。现与滚动、目录代次变化一起拦截，释放新位图并保留实际解码槽位到退出；原图完成回调同样延后几何发布。tests/waterfall-decode-regression.cjs 运行实际页面解码方法，修复前失败、修复后通过；没有增加定时器或轮询。
